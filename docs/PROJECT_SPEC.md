## 1. Назначение и границы

Единый веб-дашборд управляет парком магазинных ПК (касс) с 1С через агентов, установленных как службы Windows. Связь — по WireGuard-туннелю, сервер инициирует вызовы к агентам напрямую по их локальным IP.

| ID | Функция | Суть |
|---|---|---|
| **ФН1** | Обновление баз 1С | Слияние `.cf` / `.cfe` (с расширениями) → обновление конфигурации БД, полный цикл завершения/разрешения сеансов, парсинг логов |
| **ФН2** | Загрузка файлов по ссылке | Скачивание файлов (Яндекс.Диск, прямой URL) в рабочую папку агента, распаковка архивов, контроль целостности |
| **ФН3** | Уведомления пользователям | Уведомления 3 уровней важности, показ в сессии пользователя, фиксация «ознакомлен» по каждой сессии, отчётность в админке |

Дополнительно: мониторинг онлайн/офлайн, массовая **проверка наличия файлов обновления** на всех магазинах, очередь команд для офлайн-касс, история операций и логов.

**Вне границ (осознанно):**

1. Сервер **не хранит** файлы обновления `.cf/.cfe/.xml` — они лежат рядом с exe агента на кассе, сервер передаёт только имя файла.
2. Legacy v1 (`app.py`, `resource.py`) не переносится и не используется как образец.
3. Первая итерация **не включает**: автообновление самого агента, расписание/окно обновления по времени (этап 2), интеграцию уведомлений внутрь 1С.
4. Агент не управляет конфигурацией WireGuard (пиры добавляет ИТ вручную).

## 2. Согласованные решения

| # | Вопрос | Решение |

| Q3 | Логин и пароль пользователя 1С (`/N`, `/P`) | **Поправка (П-1):** логин **и пароль** 1С **хранятся и на сервере** — `stores.user_name_1c`, `stores.password_enc` (Fernet, ключ в секрете сервера). Пароль в UI/API/логах/аудите не раскрывается, в HTML только «задан». Доставка на агент — push-ом `POST /credentials`; агент хранит его в шифрованном конфиге (Fernet + DPAPI этой машины) |

## 3. Архитектура

### 3.1 Схема

```
                    WireGuard-туннель (1 магазин = 1 пир, статический IP)
┌─────────────────────────────────────────┐           ┌──────────────────────────────────────────┐
│ СЕРВЕР (дашборд + API)                   │  HTTP     │ КАССА: СЛУЖБА MagazAgent (LocalSystem)   │
│ FastAPI + SQLAlchemy(SQLite) + JSON API  │ ────────► │ FastAPI/uvicorn, порт 8383               │
│                                          │ ◄──────── │  ├ эндпоинты v2 (1:1)                    │
│ ├ Health Monitor  (опрос всех, 15 с)     │  (опция)  │  ├ /health /version (мониторинг)         │
│ ├ Dispatcher      (push + retry + queue) │           │  ├ мьютекс merge/update                  │
│ ├ Notification    (рассылка, приём ack)  │           │  ├ очередь уведомлений                   │
│ ├ Artifacts check (матрица файлов)       │           │  └ messenger: msg.exe + ack-протокол     │
│ └ Admin UI (SPA Vue 3, сессии админов)   │           └───────────────┬──────────────────────────┘
└─────────────────────────────────────────┘                           │ localhost:8383 (без сети)
                                                                      ▼
                                                      ┌──────────────────────────────────────────┐
                                                      │ СЕССИЯ ПОЛЬЗОВАТЕЛЯ: TrayAgent.exe        │
                                                      │ pystray + tkinter: тост/окно/topmost      │
                                                      │ [ Ознакомлен ] → POST 127.0.0.1:8383      │
                                                      └──────────────────────────────────────────┘
```

Стабильное ядро: **Python + FastAPI** и на сервере, и на агенте. Интерфейс — **SPA на Vue 3** (Vite + TypeScript + PrimeVue/Tailwind, решение П-4): сервер отдаёт JSON API `/api/v1/*` и собранную статику SPA, а Node нужен только на этапе сборки, не в проде.

### 3.2 Компоненты сервера

| Компонент | Назначение |
|---|---|
| **Admin UI** (SPA Vue 3) | Страницы: главная, магазины, карточка магазина, файлы, устройства, уведомления, задачи, аудит, настройки. Собирается Vite в `frontend\dist`, отдаётся сервером как статика |
| **Admin API** `/api/v1/admin/*` | CRUD магазинов, действия, массовые действия, уведомления, отчёты, задачи |
| **Health Monitor** | Асинхронная задача: параллельно (семафор 20, timeout 5 с) дёргает `GET /health` всех активных магазинов, обновляет `last_seen_at`, `agent_version`, `os_info` |
| **Dispatcher** | Отправляет команды на агентов; при исключении/таймауте — retry с backoff; для офлайн-магазинов держит статус `queued` и отправляет при появлении в сети |
| **Notification Service** | Рассылка уведомлений, агрегация `ack`, расчёт «X из Y», экспорт CSV |
| **Artifacts Check** | Массовый вызов `/check-files` и сборка матрицы «магазин × (cf/cfe/xml)» |
| **Devices Monitor** | Оборудование подсети магазина (Д-1): приём результатов опроса от агентов, расчёт онлайн/офлайн, сводка по магазину и глобально |
| **Credentials Service** | Логин и пароль 1С (П-1): шифрованное хранение на сервере и push на агент с проверкой `credentials_version` из `/health` |

### 3.3 Ключевые потоки

**Мониторинг (онлайн/офлайн).**
`Health Monitor` → `GET http://<ip>:<port>/health` каждые 15 с. Магазин считается **онлайн**, если был успешный ответ за последние **45 с** (3 интервала). Значение пишется в `stores.last_seen_at`; признак «онлайн» вычисляется на лету (не хранится как истина, чтобы не рассинхрониться).

**Оборудование подсети магазина (Д-1).**
Агент сам, по расписанию `device_check_interval_sec` (60 с), проверяет устройства из своего списка: `ping.exe -n 1 -w <ms> <ip>` при `check_type=icmp` либо TCP-connect при `check_type=tcp` (для камер, не отвечающих на ICMP). Результат батчем уходит на сервер, и админ видит оборудование и по каждому магазину, и сводно (`/devices`); «онлайн» = успешный ответ за последние `device_online_window_sec` (180 с). Сервер сам подсети не пингует — не зависим от того, маршрутизирует ли туннель всю подсеть магазина, а не только кассу.

**Обновление 1С (ФН1) — оркестрация сервером.**

```
1. Выбрать магазины (все / кластер / чекбоксы)
2. [ФН2] POST /download-file  {"url-file": "https://disk.yandex.ru/d/XXXX"}   → 202
3. POST /check-files {"filename": "update"}  на все  → матрица наличия в UI
4. POST /run-merge {file_name, full_merge, extension_name}                    → 202
   цикл: GET /check-merge?extension=<bool>  (5 с)  → 202 … 200/400
5. [опция] POST /send-message {"text_message": "База будет обновлена через 5 минут"}
6. POST /run-update-db {is_fast_update, extension_name}                       → 202
   цикл: GET /check-update-db?extension=<bool>     → 202 … 200/400
   внутри при is_fast_update=false: завершение сеансов → taskkill 1cv8.exe → /UpdateDBCfg → разрешение сеансов
7. Результат и текст лога — в карточке магазина и в истории задач
```

Эталонный сценарий полностью повторяет поведение v2 (см. `v2/API_DOCS.md`, `INTEGRATION_PROMPT.md` §Приложение A); меняется только инициатор — вместо человека с `curl` выступает сервер.

**Уведомления (ФН3).**

```
Админ создаёт уведомление (уровень, текст, адресация) → сервер рассылает по целевым магазинам
   ├ Сервер: POST /notify {id, title, body, severity, requires_ack, deadline, repeat_every_min}
   ├ Агент: msg.exe */localhost "<текст>"  (дублирующий быстрый канал для Important/Critical)
   ├ Агент: кладёт уведомление в локальную очередь → держит в файле, переживает перезапуск службы
   ├ TrayAgent (сессия пользователя): GET 127.0.0.1:8383/notifications/pending?session=<sid>
   │     Info      → тост 3 с, фиксируется «показано»
   │     Important → окно с кнопкой «Ознакомлен»
   │     Critical  → окно topmost + звук + повтор каждые N минут до нажатия
   └ Кнопка → POST 127.0.0.1:8383/notifications/{id}/ack {session_id, user}
         → агент: либо push на сервер POST /api/v1/agent/receipts, либо в очередь → сервер вытянет
```

**Почему TrayAgent не ходит в сеть.** Секретоносителем остаётся только служба: TrayAgent знает лишь `127.0.0.1:8383`. Это исключает попадание токена агента в пользовательскую сессию и позволяет работать уведомлениям, если касса временно не видит сервер.

## 4. Модель данных

СУБД: SQLite (файл `server\data\magaz.db`), ORM SQLAlchemy 2.0, миграции Alembic. Все таблицы — с `created_at`/`updated_at` где применимо. Переключение на PostgreSQL — только строка подключения.

### 4.1 `stores` — магазины

| Колонка | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | INTEGER PK | ✔ | |
| `name` | TEXT | ✔ | Название магазина («Имя» из ТЗ). Уникально **среди активных** магазинов (Д-11) |
| `ip_address` | TEXT | ✔ | IP кассы в WireGuard-туннеле («айпиадрес»). Уникален **среди активных** магазинов (Д-11) |
| `agent_port` | INTEGER | ✔ | Порт агента, по умолчанию `8383` |
| `cluster_name` | TEXT | ✔ | Адрес сервера 1С («имя кластера») → `/S{cluster_name}\{database_name}` |
| `database_name` | TEXT | ✔ | Имя базы 1С («имя базы данных») |
| `version_1c` | TEXT | ✔ | Версия платформы («версия 1с») → путь `<base_1c_path>/<version_1c>/bin/1cv8.exe` |
| `user_name_1c` | TEXT | ✔ | Пользователь 1С для `/N`. Логин хранится на сервере (П-1) |
| `password_enc` | TEXT | ✖ | Пароль 1С в зашифрованном виде (Fernet, ключ — в секрете сервера). В UI/API/логах/аудите не раскрывается: наружу только признак «задан» |
| `credentials_version` | INTEGER | ✔ | Версия учётных данных 1С (инкремент при смене логина/пароля). Агент докладывает свою версию в `/health` → расхождение автоматически добирается push-ом `POST /credentials` |
| `devices_version` | INTEGER | ✔ | **Д-2:** версия списка оборудования подсети (Д-1). Инкремент при любом изменении `store_devices` магазина; агент сверяет её со своей в `/health` → расхождение автоматически добирается push-ом `POST /devices/config` (§7.6) |
| `agent_token` | TEXT | ✔ | Токен агента (заголовок `X-Agent-Token`), генерируется сервером, есть кнопка «перевыпустить» |
| `agent_version` | TEXT | ✖ | Версия exe агента (самодоклад) |
| `os_info` | TEXT | ✖ | ОС кассы (самодоклад) |
| `last_seen_at` | DATETIME | ✖ | Последний успешный `GET /health`; «онлайн» = не старше 45 с |
| `is_active` | BOOLEAN | ✔ | Исключение из мониторинга и массовых операций |
| `comment` | TEXT | ✖ | |

**Уникальность имени и IP — только среди активных строк (Д-11).** `DELETE /admin/stores/{id}` — это мягкое удаление (`is_active=false`, §5.2.2), поэтому отключённый магазин **не занимает** ни имя, ни IP: кассу можно завести заново (переустановка, замена стенда), не теряя историю задач, уведомлений и аудита по старой записи. Правило обеспечено на двух уровнях: частичные уникальные индексы `uq_stores_name_active` / `uq_stores_ip_address_active` (`WHERE is_active = 1`, миграция `c4f7a1b95e20_stores_unique_active`) и проверка в сервисе (`store_service._ensure_unique`, `422` с текстом «уже существует (занят активным магазином)»). Возврат магазина в активные (`PUT {is_active: true}`) сверяется с занятыми именем и IP: конфликт → `422`, запись остаётся отключённой.

### 4.2 `admin_users` — администраторы

| Колонка | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | |

| `command_poll_timeout_sec` | `3600` | **Д-7:** предел ожидания операции 1С; дольше — задача закрывается `timeout` |

| `device_check_interval_sec` | `60` | Интервал опроса оборудования подсети агентом (Д-1) |
| `device_online_window_sec` | `180` | Окно, в котором устройство считается онлайн (Д-1) |
| `device_ping_timeout_ms` | `1000` | Таймаут одного `ping`/TCP-connect (Д-1) |

> **Д-9.** Последние три настройки живут на сервере, а не в `agent-config.json`: интервал и таймаут
> уходят агенту в теле `POST /devices/config` (`check_interval_sec`, `ping_timeout_ms`) вместе с
> списком устройств. Меняются из `/settings` без правки конфига на каждой кассе.

> **Д-10.** `notification_snooze_min` тоже серверная настройка, и она уезжает на кассу вместе с
> уведомлением (`POST /notify`, поле `snooze_min`). Кнопке «Отложить» (П-2) нужна своя локальная
> точка — `POST /notifications/{id}/snooze` (`127.0.0.1`, тело `{"session_id","session_user"}`):
> `shown`/`ack` в §5.1.2 были, а «отложить» — нет. Агент сам считает `snooze_until` и присылает
> `snoozed` вместе с `snooze_count` в пакете подтверждений; отложенное **не** считается
> ознакомленным (§4.8, §7.4, §11.5).

### 5.1 HTTP-эндпоинты агента (на кассе; вызывает сервер)

Авторизация: заголовок `X-Agent-Token`. Проверка IP источника (совпадение с `stores.ip_address`) — вторая линия. Локальные эндпоинты уведомлений принимаются **только с `127.0.0.1`** и токена не требуют.

#### 5.1.1 Перенос v2 (поведение 1:1, менять нельзя)

| POST | `/run-update-db` | `{server_name, base_name, version_1c, user_name, password?, is_fast_update?, extension_name?}` | `202` `{"message","log_path"}` |

| GET | `/api/v1/admin/notifications/summary` | **Э9:** счётчики вкладок уведомлений: по уровням (`by_severity`), по состояниям (`by_state`) и ждущие «Ознакомлен» (`unread_receipts`) |
| GET | `/api/v1/admin/jobs`, `/api/v1/admin/jobs/{id}` | История задач и логов |
| GET/POST | `/api/v1/admin/admins`, `/api/v1/admin/admins/{id}` | **Д-8 (уточнено в 1.10):** администраторы дашборда: список (действующие первыми), создание, смена пароля, блокировка (`is_active=false`), удаление. `PUT` меняет пароль и/или блокировку, `DELETE` удаляет запись; хеш пароля наружу не отдаётся, все действия — в аудите. Запреты: **себя** — `403`, **последнего действующего** администратора — `409` |
| POST | `/api/v1/admin/stores/{id}/token/rotate` | Перевыпуск токена агента |
| GET | `/api/v1/admin/stores/{id}/agent-config` | **Д-12:** данные `agent-config.json` магазина (`store_id`, `server_url`, `agent_token`, `port`, `config_path`, готовый `config_json`, подсказки). Тот же блок, что в ответе на создание, но доступен в любой момент — в том числе после перевыпуска токена; пароль 1С в конфиг не входит (П-1) |
| POST | `/api/v1/admin/stores/{id}/check` | **Д-3:** «Проверить сейчас» — живой `GET /health` агента и обновление карточки (`last_seen_at`, `agent_version`, `os_info`); ответ содержит `busy`, сессии, `work_dir`, `base_1c_path`, версии П-1/Д-1 |
| PUT | `/api/v1/admin/stores/{id}/credentials` | **Д-5:** учётные данные 1С (П-1): задать/заменить (`password`) или очистить (`clear_password`); наружу возвращается только `password_set` |
| POST | `/api/v1/agent/health` | Самодоклад агента (если касса видит сервер) |
| POST | `/api/v1/agent/receipts` | Подтверждения «ознакомлен» напрямую от агента |
| POST | `/api/v1/agent/commands/{id}/result` | Досылка результата задачи |
| POST | `/api/v1/agent/devices/status` | Батч результатов опроса оборудования подсети: `{"store_id":12,"devices":[{"ip","status","latency_ms","error"}]}` |

**Конфликты запуска (`409`) — R12 (FR-28, П-5).** `POST /admin/stores/{id}/actions` и `POST /admin/bulk/actions` **не создают** задачи `run_merge` / `run_update_db`, если запуск нарушает запрет: два магазина с одной серверной ИБ (`cluster_name` + `database_name`), повторный запуск обновления на магазине, у которого задача ещё не завершена, или ИБ, которую прямо сейчас обновляет другой магазин. Ответ — `409`, в `detail` перечислены магазины и причина («исключите их из запуска и повторите»). Массовое действие не выполняется частично: либо задачи созданы для всех выбранных магазинов, либо ни для одного.

### 7.2 Конфиг агента (`C:\MagazAgent\agent-config.json`)

```json
{
  "store_id": 12,
  "store_name": "Магазин №5",
  "server_url": "http://10.10.0.1:8080",
  "agent_token": "<выдан в дашборде>",
  "port": 8383,
  "base_1c_path": "C:/Program Files (x86)/1cv8",
  "default_file_name": "update",
  "one_c_profile": {
    "user_name": "Администратор",
    "password_enc": "<Fernet; ключ защищён DPAPI этой машины>",
    "credentials_version": 3
  },
  "msg_enabled": true,
  "notifications_poll_sec": 20,
  "work_dir": null,
  "devices_version": 4,
  "allowed_server_ips": ["10.10.0.1"]
}
```

**Д-4:** в конфиг добавлены два поля, без которых реализация канала связи (Э2) неполна:
`devices_version` — версия списка оборудования подсети, которой живёт агент (сверяется с сервером,
§7.6/Д-2), и `allowed_server_ips` — список адресов, с которых агент принимает запросы
(вторая линия защиты из §5.1). Пустой список означает «проверка источника выключена» — так
работают локальные прогоны и отладка `--console`.

Пароль 1С хранится **и на сервере** (П-1: `stores.password_enc`, Fernet), и **здесь** (Fernet + ключ под DPAPI этой машины). Сервер доставляет его push-ом `POST /credentials` — в том числе автоматически, когда версия в `/health` расходится с `stores.credentials_version`. Если в теле команды `password` не передан, агент берёт свой локальный профиль. Пароль **никогда не логируется**, не попадает в аудит, в `commands.params` и в HTML.

### 7.3 Мьютекс и состояние операций

- `merge` и `update-db` (включая расширения) выполняются строго последовательно: очередь задач + `asyncio.Lock`; второй запрос того же класса немедленно получает `409 Conflict`.
- Состояние текущей операции — в `C:\MagazAgent\agent-state.json` (тип, файл, время, лог-файл). На старте службы незавершённая операция помечается `interrupted` и доносится серверу — админ видит, что касса перезагрузилась посреди обновления.
- `is_fast_update = false` → полный цикл: предупреждение `msg.exe` (если запрошено) → завершение сеансов (`/CЗавершитьРаботуПользователей`, `/WA-`, `/AU-`, timeout 15 с) → `taskkill /f /im 1cv8.exe` → `/UpdateDBCfg` (`/UCКодРазрешения`) → разрешение работы (`/CРазрешитьРаботуПользователей`, timeout 60 с).

### 7.4 Уведомления: служба ↔ TrayAgent

- Очередь уведомлений хранится в файле `C:\MagazAgent\notifications.json` → переживает перезапуск службы и недоступность сервера.
- Служба отдаёт уведомления только на `127.0.0.1`; TrayAgent не имеет токена и не ходит в сеть.
- `ack` пользователя: агент сразу пытается `POST /api/v1/agent/receipts`; при неудаче держит в буфере и досылает позже.
- `msg.exe */localhost "<текст>"` вызывается службой для `important`/`critical` (если `msg_enabled`) как дублирующий канал; результат пишется в лог, «нет сеансов» — нормальная ситуация для выключенного ПК.
- Уровни: `info` — тост 3 с (фиксируется `shown`); `important` — окно с кнопкой «Ознакомлен»; `critical` — окно `topmost` + звук + повтор каждые `repeat_every_min` до нажатия.
- **Кнопка «Отложить» (П-2).** Оставляет уведомление непрочитанным (`snoozed`), убирает окно из видимости и возвращает его через `notification_snooze_min` (по умолчанию 15 мин, настройка сервера). Автовсплытие — только для `important`/`critical`; `info` сам не всплывает: висит в трее до тех пор, пока пользователь не откроет интерфейс и не нажмёт «Ознакомлен». Число откладываний не ограничиваем, но пишем `snooze_count`/`snooze_until` — в отчёте видно, кто систематически «откладывает».
- Учёт по сессиям: у каждого вошедшего пользователя своё окно и свой `receipt` (Q50: 1–2 сессии на кассу).
- **Режимы трея (Э6, §7.5).** `MagazTrayAgent.exe` собирается **без консоли** (окно на экране кассира недопустимо), логи — `C:\ProgramData\MagazAgent\logs\tray.log` (каталог тот же, что у службы). Диагностика без GUI: `--console` (печатать действия вместо окон), `--pending` (что ждёт «Ознакомлен»), `--once` (один цикл опроса), `--ack <id>` и `--snooze <id>` (подтверждение из текущей сессии). Решение «тост или окно, пора ли повторить» вынесено в `client\tray\presenter.py` и покрыто тестами; `pystray` и `tkinter` в проверках не участвуют.
- **Окно уведомлений (Э9, §7.4).** Уведомления показывает не набор всплывающих окон, а одно окно в
  правом верхнем углу: вкладки «все / информация / важно / критично» и «справочник» со счётчиками,
  список слева, тело справа — с разметкой, списками и картинками (`client/tray/__main__.py`,
  `TrayWindows`). Размер считает `panel_geometry` (`client/tray/presenter.py`): не больше 15 %
  площади экрана, окно прижато к правому верхнему краю. Для `critical` оно поднимается поверх всех
  (`topmost`) и со звуком. Кнопки: «Свернуть» — убрать в трей (счётчик непрочитанных остаётся),
  «Ознакомлен» и «Отложить» (П-2). «Справочник» — прочитанное, оставленное на кассе: служба отдаёт
  его по `GET /notifications/archive`, а касса держит такие уведомления в `notifications.json`.
  Картинки окно берёт **из локального кэша** (`C:\MagazAgent\notifications-images\<id>\<имя>`):
  агент скачивает их фоном при `POST /notify`, а окно просит `GET /notifications/{id}/images/{name}`
  у службы на `127.0.0.1` — в сеть окно не ходит и картинку не перескачивает. Ширина картинки приходит из тела (`style="width: …"`): проценты считаются от ширины области тела, пиксели — как задал админ, но не шире окна и не меньше 60 px. Разбор разметки
  вынесен без GUI (`client/tray/richtext.py`, §13) и покрыт тестами, как и решение «тост или окно»
  (`client/tray/presenter.py`).
- **Справочник сотрудников не ведём (ответ на вопрос 2, П-6).** Адресат уведомления — учётная запись Windows, а не человек из списка: уведомление показывает тот, кто сейчас запущен на кассе. Поэтому в `notification_receipts` лежат `session_user`/`session_id` (§4.8), а «X из Y» считается по сессиям.
- **Прокси не участвует (находка живой приёмки Э7).** Служба и трей обращаются к `127.0.0.1` в обход прокси: `httpx` по умолчанию берёт прокси из окружения и настроек ОС, из-за чего на машине с системным прокси запрос трея получал `503` и уведомления не показывались (служба была жива). В `TrayAgentClient` задан `trust_env=False` (регресс-тест `TestProxyIsIgnored`), в `AgentClient` — так же.

### 7.5 Режим разработки

- `magaz-agent.exe --console` — то же приложение в терминале (без SCM) с человекочитаемым логом. Обязательный режим: иначе на кассе нечего смотреть.
- Все внешние процессы (`1cv8.exe`, `msg`, `taskkill`) инжектируются через провайдер → в тестах подменяются моками; реальная 1С и сеть не нужны.

### 7.6 Опрос оборудования подсети (Д-1, новая функция)

| Свойство | Значение |
|---|---|
| Источник списка | Сервер push-ит список агенту (`POST /devices/config`, вместе с `devices_version`); агент хранит копию в `C:\MagazAgent\devices.json` — опрос продолжается и когда сервер недоступен |
| Проверка | `icmp` → `ping.exe -n 1 -w <timeout_ms> <ip>` (argv, **без shell**); `tcp` → TCP-connect на `check_port` (`asyncio.open_connection`) |
| Расписание | Каждые `device_check_interval_sec` (60 с); параллелизм ограничен семафором (не более 16 проверок одновременно), чтобы не мешать кассе. **Д-9:** интервал и таймаут одной проверки приходят агенту в push-е списка (`check_interval_sec`, `ping_timeout_ms`), поэтому меняются из `/settings` без правки `agent-config.json` на кассах |
| Отчёт на сервер | Батч `POST /api/v1/agent/devices/status` (`ip`, `status`, `latency_ms`, `error`); при недоступности сервера — буфер и досылка (как `ack`) |
| «Проверить сейчас» | `POST /devices/check-now` от сервера — внеочередная проверка списка IP, ответ синхронный |
| Синхронизация списка | `devices_version` у магазина на сервере ↔ версия в `/health` агента; расхождение → автоматический повторный push списка |
| Запрещено | Сканирование подсети «наугад» (sweep) — проверяем только явно заведённые устройства |

## 8. Безопасность

### 8.1 Контуры защиты

| Контур | Механизм |
|---|---|
| Сеть | WireGuard-туннель: посторонние физически не видят ни дашборд, ни агентов |
| Агент ← сервер | Заголовок `X-Agent-Token` (уникальный на магазин, выдан сервером, хранится в конфиге) |
| Дополнительно | Проверка **IP источника** запроса против `stores.ip_address` — даже с украденным токеном запрос из другой сети отклоняется |
| Пользователь → служба | Эндпоинты уведомлений принимаются **только с `127.0.0.1`**; TrayAgent не имеет токена и не ходит в сеть |
| Админ → дашборд | Логин/пароль (хеш), подписанная cookie, аудит действий в `audit_log` |
| Секреты 1С | Пароль `/P` хранится **шифрованным и на сервере** (`stores.password_enc`, Fernet; ключ — в секрете сервера), и на агенте (Fernet + DPAPI машины). В UI/API — только признак «задан». Подробно — §8.3 |
| Инъекции | Команды 1С запускаются **списком аргументов без shell** (`create_subprocess_exec`), имя файла санитайзится (basename, запрет `/`, `\`, `.`, `..`); пинг устройств — тоже argv `ping.exe` |
| Логи | Пароль никогда не попадает в логи, в `commands.params`, в ответы API, в аудит и в HTML (в UI — маска) |
| Оборудование подсети | Проверяем только IP из `store_devices` магазина: никаких сканирований диапазонов; лимит параллелизма, чтобы не «положить» кассу |

### 8.2 Что осознанно не делаем в первой итерации

- HTTPS на дашборде (туннель уже шифрует) — опция через реверс-прокси.
- Роли администраторов (один уровень прав) — но таблица `admin_users` и аудит позволяют добавить роли без ломки схемы.
- Ротация токенов по расписанию — есть только ручная кнопка «перевыпустить».
- **Экспорт истории операций (Excel/CSV) и отчётов по обновлениям за период** — не нужен (ответ заказчика на вопрос 3, П-8). CSV остаётся только в отчёте по уведомлениям (§11.5).
- **Интеграции с ИТ-системами** (мониторинг, тикеты) — не в первой итерации (ответ на вопрос 4, П-7). Возможное развитие — Telegram-бот с алертами «магазин или устройство подсети офлайн более N минут» (§12 Э8).

### 8.3 Хранение учётных данных 1С (П-1)

| Аспект | Решение |
|---|---|
| Где лежит | Сервер: `stores.user_name_1c`, `stores.password_enc` (Fernet). Агент: `one_c_profile.password_enc` (Fernet, ключ под DPAPI машины) |
| Ключ сервера | `server\data\secrets.key` (права — только у администратора сервера) или переменная окружения `MAGAZ_SECRET_KEY`. Ключ секретов **отдельный** от ключа подписи cookie |
| В API и UI | Пароль не отдаётся ни в JSON, ни в HTML: только `password_set: true/false` и кнопки «задать / заменить / очистить» |
| Передача | Только push-ом `POST /credentials` внутри туннеля; пароль не попадает в `commands.params`, логи, аудит, HTML и в вывод `format_command()` (маскируется) |
| Аудит | Пишется факт: «учётные данные 1С изменены админом X, время» — без значения |
| Синхронизация | `stores.credentials_version` ↔ версия в `/health` агента; расхождение → автоматический повторный push (агент самолечится после переустановки/потери конфига) |
| Ротация ключа | Процедура в RUNBOOK: перешифровать `password_enc` всех магазинов новым ключом + повторно разослать `POST /credentials` |

## 11. Веб-дашборд: страницы и действия

### 11.1 Главная (`/`)

- Плитки: **Магазинов в работе** (активные магазины, Д-14), **Онлайн**, **Офлайн**, **Устройства онлайн/всего** (Д-1), **Активных уведомлений (ждут ознакомления)**, **Задач в работе**.
- Плитка магазинов считает **магазины в работе** (`counts.stores_active`), а не строки таблицы: отключённый кнопкой «Отключить» магазин (§5.2.2) остаётся в БД ради истории, отчётов и повторного включения, поэтому его число показывается отдельно (`counts.stores_inactive` — подсказка «активных · отключено N») — Д-14. Сумма «онлайн» и «офлайн» считается по тем же активным магазинам.
- **Раскрывающийся список магазинов**: строки Имя / IP / Кластер / БД / Версия 1С / Статус (зелёный-красный) / Последняя активность / Последняя операция.
- Раскрытие строки: файлы (cf/cfe/xml с размерами и датами), статус текущей операции, устройства подсети со статусами (Д-1), кнопки быстрых действий.
- Каждые ~10 с — автообновление через polling JSON API (Pinia-стор + `setInterval`), без перезагрузки страницы; есть и ручная кнопка «Обновить».
- Фильтры: кластер, статус, поиск по имени/IP/БД.
- **Тема оформления (Д-13).** В шапке дашборда — переключатель «Светлая тема / Тёмная тема / Как в системе». Выбор хранится в браузере (`localStorage`), применяется до монтирования SPA (без «вспышки») и действует на все страницы; режим «как в системе» следит за настройкой ОС, а тёмная тема переключается классом `.app-dark` на `<html>` — тем же классом PrimeVue меняет свои токены.

### 11.2 Магазины (`/stores`, `/stores/{id}`)

- CRUD: колонки ТЗ (Имя, IP, Кластер = сервер 1С, БД, Версия 1С) + порт, **учётные данные 1С** (логин + пароль: поле пароля всегда пустое, показывается только признак «задан», рядом «заменить»/«очистить» — П-1), **устройства подсети** (Д-1), активность, комментарий.
- При создании магазина сервер генерирует `agent_token` и показывает блок «что вписать в конфиг агента» (store_id, server_url, token) — с кнопкой «скопировать». **Тот же блок открывается в любой момент (Д-12):** кнопка «Конфиг» у строки магазина и в карточке читает `GET /admin/stores/{id}/agent-config`, показывает готовый `config_json` и даёт «Скопировать JSON», «Скопировать токен» и «Скачать agent-config.json» — так конфиг собирается заново после переустановки кассы или перевыпуска токена.
- **Правка всех параметров (Э8).** Форма «Изменить магазин» (из списка и из карточки) правит все колонки §4.1: имя, IP, порт агента, кластер и базу 1С, версию, логин 1С, комментарий и признак «магазин активен». Пароль 1С — отдельные действия «задать/заменить» и «очистить» (`PUT /stores/{id}/credentials`, П-1): в запрос `PUT /stores/{id}` он не подмешивается, наружу виден только признак «задан».
- **Имя и IP можно переиспользовать после отключения (Д-11).** «Отключить» — мягкое удаление, поэтому магазин с тем же именем и IP заводится заново, а конфликт (`422`) возникает только с **активным** магазином; включить обратно магазин, чьё имя или IP занял активный, нельзя — сервер откажет и оставит запись отключённой. В форме об этом есть подсказка.
- Кнопка «Перевыпустить токен» с предупреждением, что агент потребуется перенастроить (после ротации агент отвечает `401`).
- Карточка: текущий статус, версия агента, ОС, рабочая папка, `base_1c_path`, `busy`, список активных сессий, история задач магазина, логи, активные уведомления, **таблица оборудования подсети** с кнопками «добавить», «проверить сейчас», «отключить из опроса» (Д-1).
- **Кнопка «Проверить сейчас» (Д-3).** Делает живой `GET /health` агента: карточка показывает `busy`, сессии, рабочую папку и `base_1c_path` (в таблице `stores` их нет) и обновляет `last_seen_at`, `agent_version`, `os_info`. Касса не ответила — `503`, магазин остаётся «офлайн».

### 11.3 Файлы (`/files`)

- Матрица «магазин × (cf/cfe/xml)»: галочка/крестик, размер, дата файла, время последней проверки.
- Кнопка «Проверить на всех» (или на выбранных) с полем «имя файла».
- Красная подсветка магазинов, где нужного файла нет; счётчик «файл есть у N из M».
- Кнопка «Разослать ссылку» (ФН2): поле URL + выбор магазинов → `POST /download-file` → затем повторная проверка.
  **Д-6:** повторная проверка выполняется **отдельной задачей** `check_files`, которую сервер заказывает сам,
  когда файл появился в рабочей папке кассы: в истории видно и скачивание, и проверку, а снимок
  (размер, дата — Q52) попадает в `file_checks` тем же путём, что и при ручной кнопке «Проверить».
- Пока задача `download_file` не завершена, диспетчер опрашивает `/check-files` и закрывает её `success`
  только тогда, когда файл реально виден на кассе; иначе — `timeout` по `command_poll_timeout_sec` (Д-7).

### 11.4 Операции

- **Слияние**: имя файла, чекбокс `full_merge`, опционально `extension_name` → предупреждение при отсутствии файла (Q53) → запуск.
- **Обновление БД**: `is_fast_update` (по умолчанию «полный цикл с завершением сеансов»), опционально `extension_name`.
- **Сообщение пользователям**: текст → `POST /send-message` (с явным предупреждением «завершит 1cv8.exe у всех»).
- **Жёсткий запрет одновременного обновления одной ИБ (R12, FR-28, П-5).** Перед запуском `run_merge` / `run_update_db` сервер проверяет: не совпадают ли у выбранных магазинов `cluster_name` + `database_name`, нет ли у магазина незавершённой задачи обновления, не обновляет ли эту же ИБ другой магазин. Любое совпадение — отказ `409`, задачи не создаются вовсе (массовый запуск не выполняется частично), а в тексте перечислены магазины и что исключить. Кнопки «Проверить файлы», «Разослать ссылку» и «Сообщение» не блокируются: они ИБ не меняют. Офлайн-магазин конфликтом не считается — задача ждёт в очереди.
- Массовые действия: выбор магазинов или «весь кластер»; прогресс-таблица по каждому магазину с итогом `success`/`failed`/`queued`.
- Опрос `/check-merge` и `/check-update-db` — серверный `dispatcher`, каждые 5 с; результат и текст лога видны в задаче и в карточке магазина.
- **Д-6 (наблюдение этапа Э3):** одного `/check-*` мало — если 1С не запустилась, лог остаётся пустым, а
  `/check-*` честно отвечает `202 in_progress`. Поэтому диспетчер дополнительно спрашивает `/health`:
  касса не занята (`busy`) и/или в `agent-state.json` есть прерванная операция → задача закрывается
  `failed` с текстом причины, а не «висит» до таймаута. То же правило закрывает случай «касса
  перезагрузилась посреди обновления» (§7.3).

### 11.5 Уведомления (`/notifications`)

- Форма: заголовок, текст, уровень (`info`/`important`/`critical`), адресация (все / кластер / магазины), `requires_ack`, дедлайн, интервал повтора, дублировать ли через `msg.exe`.
- **Редактор и предпросмотр (Э9):** текст набирается в редакторе (`frontend/src/components/RichTextEditor.vue`, TipTap): жирный/курсив/подчёркивание/зачёркнутый, заголовки h2–h3, списки, цитата, разделитель, ссылки `http(s)`/`mailto`, цвет и подсветка, выравнивание, картинка кнопкой, перетаскиванием или из буфера (png/jpeg/gif/webp, ≤ 2 МБ, ≤ 10 на уведомление). Разметку проверяет сервер (`shared.richtext`), а «Просмотреть» открывает `NotificationBody` — то же сообщение, что увидит кассир. Галочка «простой текст» оставляет прежний ввод (`body_format=plain`). Картинка видна в редакторе сразу: метка `magaz-image:<имя>` показывается черновиком, а размер меняется кнопками панели («−», «+», «50 %», «100 %», «как есть») или перетаскиванием ручки в углу — ширина уезжает в тело стилем `width`, и её уважают и предпросмотр, и окно кассы (§7.4).
- **Вкладки по важности и «удалять после прочтения» (Э9):** вкладки «все / информация / важно / критично» со счётчиками уведомлений и ждущих «Ознакомлен» (`severity_counts`/`unread_by_severity` из того же ответа списка); в строке видно «с разметкой · картинок N · удаляется после прочтения», а тело показывается текстом, а не разметкой. `delete_after_read` задаётся в форме: `false` — прочитанное остаётся справочником на кассе, `true` — исчезает из окна (§7.4). Отчёт `/notifications/{id}` рисует тело тем же `NotificationBody`, включая картинки (адрес картинки отдаёт `imageUrl(id, name)`).
- Список: создатель, время, охват, **«ознакомлены X из Y»**, прогресс-бар, статус (в работе/завершено/отменено), кнопка «отменить».
- Карточка уведомления: таблица по магазинам → по сессиям (пользователь, статус, время показа, время ознакомления), экспорт CSV.
- Здесь же — ручное разовое «Сообщение пользователям» (`/send-message`) для коротких предупреждений.
- **Адресат — учётная запись Windows** (ответ на вопрос 2, П-6): справочника сотрудников нет, «X из Y» считается по активным сессиям кассы (§4.8), поэтому «ознакомлен» фиксируется тем пользователем, который в этот момент работает за ПК.
- Кнопка **«Отложить»** (П-2): в карточке уведомления по каждой сессии видно `snooze_count` и «отложено до»; интервал возврата — `notification_snooze_min` в `/settings`. Автоповтор — только для `important`/`critical`; `info` не всплывает сам и ждёт явного «Ознакомлен».

### 11.6 Задачи (`/jobs`), аудит (`/audit`), настройки (`/settings`)

- `/jobs`: фильтры по магазину/типу/статусу/датам, полный лог задачи, ссылки на связанные уведомления. **Экспорта истории операций нет** (ответ заказчика на вопрос 3, П-8): история читается в UI и живёт в БД (`commands` + `job_logs`), CSV — только в отчёте по уведомлениям (§11.5).
- `/audit`: кто создал/изменил магазин, кто запускал операции и уведомления, перевыпуск токенов, входы.
- `/settings`: интервалы мониторинга, интервалы опроса оборудования подсети, значения по умолчанию, **управление администраторами** (Д-8: список, создание, смена пароля, блокировка).

### 11.7 Оборудование подсети (`/devices`, Д-1)

- Сводная таблица: магазин, имя, IP, тип, способ проверки (`icmp` / `tcp:порт`), статус (зелёный `online` / красный `offline` / серый `unknown`), задержка, время последнего ответа, комментарий.
- Фильтры: магазин, кластер, тип устройства, статус; поиск по имени и IP.
- Действия: «Проверить сейчас» (по строке и по всему магазину), «Добавить устройство» (имя, IP, тип, способ проверки), «Отключить из опроса» (soft-delete `is_active=false`).
- Офлайн-устройства подсвечиваются красным; серый `unknown` означает «нет данных с кассы», а не «нет связи с камерой».
- Плитка главной «Устройства онлайн/всего» ведёт сюда с предустановленным фильтром «офлайн».
- **Д-9.** Расписание опроса (`device_check_interval_sec`) и таймаут проверки (`device_ping_timeout_ms`) — серверные настройки §4.9: меняются в `/settings` и уезжают на кассы в теле `POST /devices/config` при следующей синхронизации списка, вручную конфиг агента править не нужно.

## 13. Тестирование

Без реальной 1С и без сети: все внешние вызовы инжектируются и подменяются моками.

### 13.1 Перенос тестов v2 (32 шт.; смысл сохраняем, фреймворк — `pytest`)

| Группа | Что проверяется |
|---|---|
| Сборка команд слияния | основная конфигурация, `full_merge`, расширение (`.cfe`, без `-Settings`), пустой пароль не передаётся, `/DisableStartupMessages`, `/UC…`, метасимволы остаются внутри одного аргумента |
| Сборка команд обновления БД | основная/расширение, наличие `/UpdateDBCfg`, `/Out` |
| Завершение и разрешение сеансов | `ENTERPRISE`, `/CЗавершитьРаботуПользователей`, `/WA-`, `/AU-`, `/CРазрешитьРаботуПользователей`, `/UCКодРазрешения` |
| Состояния лог-файла | `not_found`; пустой лог = `in_progress`; успех; ошибка (`Ошибка`); нераспознанный текст; `clear_log_file` |
| API-контракт | коды `200/202/400/422`, формат `{"status","message","logs"}`, `202` на `/run-*` |

### 13.2 Новые тесты

| Группа | Что проверяется |
|---|---|
| Мьютекс | параллельные `merge`/`update` → второй получает `409`; блокировка снимается после ошибки/timeout |
| Состояние операции | после «перезагрузки» (пересоздание агента) операция помечается `interrupted` |
| Безопасность путей | имя файла с `/`, `\`, `..`, абсолютный путь → `422`; ZIP с `../` не распаковывается (Zip Slip) |
| Токен и IP | неверный `X-Agent-Token` → `401`; запрос с чужого IP → `403`; эндпоинты уведомлений — только `127.0.0.1` |
| Секреты | пароль отсутствует в логах, в `commands.params`, в ответах API и в аудите |
| Мониторинг | успех/таймаут/ошибка `GET /health` → корректные `last_seen` и онлайн-статус; окно 45 с |
| Диспетчер | офлайн-магазин получает `queued`; при появлении в сети команда уходит; retry с backoff; лимит попыток; после перезапуска сервера очередь подхватывается заново (FR-24) |
| Опрос `/check-*` | переходы `202 → 200` и `202 → 400`, корректное сохранение лога в задачу |
| Незавершённая операция (Д-6) | «залипший `202`» при свободной кассе → `failed` с причиной; `interrupted_operation` в `/health` → `failed` «прервана»; превышение `command_poll_timeout_sec` → `timeout` |
| ФН2 → проверка (Д-6) | `download_file` закрывается только после появления файла в `/check-files`, затем сервер сам создаёт задачу `check_files`, и её снимок попадает в `file_checks` |
| П-1 на сервере | расхождение `credentials_version` → push `POST /credentials` с расшифрованным паролем; при совпадении версий push не выполняется; период сверки — `credentials_push_interval_sec` (Д-7) |
| П-1 на агенте | `POST /credentials` пишет профиль в `agent-config.json` и в `/health`; пароль зашифрован (Fernet + DPAPI), в логи не попадает; при `password` в теле команды он главнее профиля (§5.1.1) |
| Уведомления | адресация (все/кластер/список); `ack` по каждой сессии; «X из Y»; дедлайн → `expired`; повтор для `critical` |
| Офлайн-устойчивость | сервер недоступен → `ack` и результат уходят в буфер и досылаются позже |
| Сервер | вход/выход, CRUD магазинов, перевыпуск токена, доступ к страницам, аудит |
| SPA (П-4) | `npm run build` без ошибок; Vitest: api-клиент пробрасывает `401` на экран входа и показывает `409` как конфликт операции; маршруты §5.2.1 открываются после сборки (history-fallback) |
| Учётные данные (П-1) | пароль не встречается ни в HTML, ни в JSON, ни в логах, ни в аудите, ни в `commands.params`; `POST /credentials` меняет версию на агенте; расхождение версии в `/health` → автоматический повторный push |
| Отложенные уведомления (П-2) | «Отложить» → `snoozed` + `snooze_count+1`, окно скрыто; возврат через `notification_snooze_min` только для `important`/`critical`; `info` сам не всплывает и ждёт «Ознакомлен» |
| Оборудование подсети (Д-1) | ICMP-проверка и TCP-connect на моках; команда собирается списком argv (без shell); окно `device_online_window_sec`; агент недоступен → `unknown`, а не `offline`; CRUD устройств и «проверить сейчас» на сервере. **Д-9:** интервал и таймаут из push-а списка применяются агентом без перезапуска службы |
| Запрет R12 (П-5) | `run_merge`/`run_update_db` по двум магазинам одной ИБ (`cluster_name` + `database_name`) → `409`, ни одной созданной задачи; повторный запуск при незавершённой задаче магазина → `409`; та же ИБ у другого магазина → `409`; `check_files`/`download_file`/`send_message` по тем же магазинам → `202`; после завершения задачи запуск проходит |
| Отсутствие экспорта (П-8) | У API задач нет CSV-выгрузки; `?format=csv` поддерживает только отчёт по уведомлению (§11.5) |
| Администраторы (Д-8) | CRUD `admin_users`: создание, смена пароля, блокировка, удаление; хеш пароля не появляется в ответах API и в аудите; себя (`403`) и последнего действующего (`409`) трогать нельзя; заблокированный не входит и теряет ранее выданную cookie |
| Предполётная проверка (Э7) | сервер: версия Python и зависимости, все 11 таблиц §4.1, ревизия Alembic, ключи §8.3, собранный `frontend\dist`, настройки §4.9, действующий администратор, порт, каталоги логов, `public_server_url`; касса: конфиг §7.2, доступность `GET /api/v1/health`, каталог версий с `1cv8.exe`, `msg.exe`, порт агента, рабочая папка и логи, доставленные учётные данные 1С. Ошибка (`fail`) останавливает приёмку, `warn` — нет; пароль и токен в отчёт не попадают; текст отчёта печатается в cp1251-консоли |
| Трей, служба и развёртывание (Э6) | Сессия Windows → `SessionRef`; клиент ходит только на `127.0.0.1` и **без** токена; `info` — тост один раз, `important` — окно с кнопками, `critical` — повтор по `repeat_every_min`; `ack`/`snooze` не теряются при недоступной службе; режимы CLI трея (`--pending`, `--once`, `--ack`, `--snooze`); команды службы без `pywin32` дают код 3 и подсказку; спеки и bat-скрипты ссылаются на те же имена (`magaz-agent.exe`, `MagazTrayAgent.exe`, задача `MagazTrayAgent`), что и код |

### 13.3 Что нельзя проверить без стенда

Реальное поведение `1cv8.exe`, `msg.exe`, `taskkill`, службы под `LocalSystem` и Windows-сессий проверяется только на живой кассе/тестовой базе (этап Э7). На машине разработки 1С не установлена, поэтому Э7 выполняется на стенде заказчика по чеклисту Приложения A.

## 14. Развёртывание и эксплуатация

### 14.1 Сервер

1. Python-окружение, `pip install -r requirements.txt`.
2. `alembic upgrade head`; создание первого администратора CLI-командой.
3. Запуск: `python -m server.main` (uvicorn) либо как служба Windows (PyInstaller + `install_service.bat`) — на усмотрение ИТ.
4. Настройки: `server/config.py` / переменные окружения (порт, путь БД, секрет cookie, значения из §4.9). Файл секретов `server\data\secrets.key` (ключ Fernet для пароля 1С, П-1) — создаётся при первом запуске, права только у администратора сервера, в бэкап БД не входит; порядок хранения описан в RUNBOOK.
5. Фронтенд (SPA, П-4): `cd frontend && npm ci && npm run build` → `frontend\dist`. Сервер отдаёт эту папку сам — отдельный веб-сервер не нужен, Node требуется только на сборочной машине.

### 14.2 Касса (агент)

1. Скопировать `C:\MagazAgent\` (exe + `agent-config.json` + TrayAgent).
2. Вписать `store_id`, `server_url`, `agent_token` (берутся в карточке магазина), `base_1c_path`, профиль 1С.
3. Запустить `install_agent.bat` (AD-агностично):
   - `magaz-agent.exe install` → автозапуск при старте системы → `start`;
   - регистрация TrayAgent: `schtasks /create /tn MagazTrayAgent /tr "C:\MagazAgent\MagazTrayAgent.exe" /sc onlogon /f` (без домена `/ru Users`; в домене `\ru "ДОМЕН\Пользователи"`).
4. Проверка: магазин в дашборде стал «онлайн», в карточке видны версия агента, ОС, рабочая папка, `base_1c_path`.
5. Положить файлы обновления (`.cf`, `.cfe`, `.xml`) в `C:\MagazAgent\` и нажать «Проверить файлы».

### 14.3 Обновление агента (первая итерация — вручную)

Остановить службу → заменить `magaz-agent.exe` / TrayAgent → запустить. Автоматическое самообновление — этап Э8.

### 14.4 Эксплуатационный минимум

- **Бэкап** `server\data\magaz.db` (SQLite — файл; при простое копирование безопасно).
- **Ротация** логов сервера и агента.
- **Диагностика на кассе**: `magaz-agent.exe --console`, файл `log-1cv8-console.txt`, `C:\ProgramData\MagazAgent\logs\agent.log`.

### D.4 Правила обработки

1. **Один пункт = одно изменение.** Несколько разных правок в одном пункте — это несколько строк.
2. **Приоритет.** Правки, затрагивающие §4 (модель данных), §5 (API) и §10 (инварианты), вносятся **до** старта этапа, который их использует. Если этап уже начат — правка делается вместе с миграцией и тестом, и это указывается в отчёте по этапу.
3. **Обратная связь.** По каждому пункту исполнитель либо вносит правку и ставит `внесено` с указанием раздела, либо ставит `уточнение` и задаёт вопрос, либо `отклонено` с причиной.
4. **Версионность.** Каждое принятое изменение поднимает версию документа (см. D.3) и, если оно меняет поведение уже принятых решений, помечается ссылкой на решение (`Q<n>` / `FR-<n>` / `I-<n>`).
5. Приложение D в код не переносится — это рабочий журнал согласования.

Монорепозиторий проекта по спецификации [`docs/PROJECT_SPEC.md`](docs/PROJECT_SPEC.md)
(версия **1.11**). Документ — единственный источник истины: структура репозитория (§6),
модель данных (§4), API (§5), инварианты (§10), план этапов (§12).

**Статус: этапы Э1 «Каркас» — Э6 «Сборка и развёртывание» — выполнены; Э7 «Приёмка»
подготовлена** (перечень в конце этого файла). Протокол приёмки —
[`docs/ACCEPTANCE.md`](docs/ACCEPTANCE.md), установка — [`docs/INSTALL.md`](docs/INSTALL.md),

## Быстрый старт: сервер

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt

.venv\Scripts\python.exe -m alembic upgrade head        # создаёт server\data\magaz.db
.venv\Scripts\python.exe -m server.cli create-admin --username admin   # пароль спросит интерактивно
.venv\Scripts\python.exe -m server.main                 # http://127.0.0.1:8080
```

Конфигурация — переменные окружения с префиксом `MAGAZ_` и/или файл `.env` в корне
(`server/config.py`): `MAGAZ_HOST`, `MAGAZ_PORT`, `MAGAZ_DATABASE_URL`, `MAGAZ_LOG_LEVEL`,
`MAGAZ_SECRET_KEY`, `MAGAZ_COOKIE_SECRET`, `MAGAZ_SERVE_SPA` и др.

Служебные команды (§14.1): `create-admin`, `list-admins`, `reset-password`, `seed-settings`,
`info` — `python -m server.cli <команда> --help`.

Рабочие файлы сервера (`server\data\`): БД `magaz.db`, ключ шифрования паролей 1С
`secrets.key`, ключ cookie `cookie_secret.key`, логи `logs\server.log`. Каталог **не**
коммитится и создаётся автоматически при старте (инвариант I-10: импорт модулей без
сайд-эффектов).

## Быстрый старт: фронтенд

```powershell
cd frontend
npm ci
npm run build      # vue-tsc --noEmit + vite build → frontend\dist (её отдаёт сервер)
npm run dev        # режим разработки, /api проксируется на http://127.0.0.1:8080
```

Node нужен **только на сборке**: сервер отдаёт уже собранный `frontend\dist`
(`server/api/spa.py`: статика + history-fallback для маршрутов SPA). Пока `dist` не собран,
на `/` отдаётся страница-заглушка `503` с инструкцией по сборке, а `/api/v1/*` работает штатно.

## Быстрый старт: агент кассы (Э2)

1. В дашборде создать магазин (`/stores` → «Добавить магазин») и скопировать блок
   «Что вписать в конфиг агента».
2. Положить `agent-config.json` (§7.2) рядом с агентом (по умолчанию `C:\MagazAgent\`):

```json
{
  "store_id": 1,
  "store_name": "Магазин №5",
  "server_url": "http://10.10.0.1:8080",
  "agent_token": "<из дашборда>",
  "port": 8383,
  "base_1c_path": "C:/Program Files (x86)/1cv8",
  "default_file_name": "update",
  "devices_version": 1,
  "allowed_server_ips": ["10.10.0.1"]
}
```

3. Запустить агент (пока без службы Windows — она появится на Э6):

```powershell
.venv\Scripts\python.exe -m client.agent --console          # лог в терминал
.venv\Scripts\python.exe -m client.agent info               # что прочитано из конфига
.venv\Scripts\python.exe -m client.agent --config C:\MagazAgent\agent-config.json
```

Через интервал мониторинга (15 с) магазин в дашборде станет «онлайн»; кнопка
«Проверить сейчас» в карточке делает живой `GET /health` и показывает `busy`, сессии,
рабочую папку и `base_1c_path`.

### Отклонения и решения, принятые по ходу этапа

1. **Д-2 (добавка в спецификацию).** §7.6 и §5.1.2 требуют сверять `devices_version`, но
   в §4.1 такого поля у `stores` не было. Добавлено
   `stores.devices_version` (INTEGER, по умолчанию 1); спецификация поднята до версии 1.4
   (§4.1 и Приложение D).
2. **Стиль заглушек.** Страницы будущих этапов отдают `StagePlaceholder` с перечнем того,
   что появится на этапе, — чтобы навигация была проверяема уже сейчас.
3. **Ожидание сессии в `App.vue`.** Оболочка с меню не монтируется, пока сессия не
   проверена, иначе она успевает опросить защищённые эндпоинты и в консоль летят лишние
   `401`. На время проверки показывается «Проверяем сессию…».
4. **`logout` не падает при недоступном сервере.** Ошибка выхода гасится: локальное
   состояние всё равно сбрасывается, иначе пользователь «застревает» в интерфейсе.
5. **`@types/node` в devDependencies** — нужен `vite.config.ts` для `node:url` при
   `vue-tsc --noEmit`.

### Отклонения и решения, принятые по ходу этапа

1. **Д-3, Д-4, Д-5 (добавки в спецификацию; версия документа 1.5).**
   - Д-3: `POST /api/v1/admin/stores/{id}/check` — «Проверить сейчас»: §11.2 требует показывать
     `busy`, сессии и рабочие пути, а колонок под них в `stores` нет, значит их нужно запрашивать
     живьём (ответ агента ошибкой → `502`, недоступен → `503`; код `502` добавлен в Приложение B).
   - Д-4: канал связи агента — `GET /`, `/health`, `/version`; в `agent-config.json` добавлены
     `devices_version` (сверка списка оборудования, Д-1/Д-2) и `allowed_server_ips` (вторая линия
     защиты из §5.1: список адресов сервера; пусто — проверка выключена).
   - Д-5: `PUT /api/v1/admin/stores/{id}/credentials` — задать/заменить/очистить учётные данные 1С
     (§8.3 требовал кнопки, но точки их применения в API не было).
2. **`trust_env=False` в клиенте агентов (найдено живым прогоном).** На машине разработки в
   настройках ОС зарегистрирован локальный прокси, и `httpx` по умолчанию отправлял туда даже
   обращения к `127.0.0.1:8383` — отвечал прокси (`503` с пустым телом), а не агент. Теперь
   мониторинг и «Проверить сейчас» игнорируют прокси-настройки: агенты живут на приватных адресах
   туннеля. Регресс — `tests/server/test_client_http.py::TestProxyIsIgnored` (при `trust_env=True`
   тест падает).
3. **Поиск и уникальность — в Python (`casefold`), а не SQL `lower()`.** SQLite приводит регистр
   только для латиницы, поэтому «Магазин №5» и «магазин №5» через SQL считались бы разными: это
   ломало и проверку дубликата имени, и поиск по списку.
4. **Health Monitor выключен в тестовой сборке приложения**
   (`MAGAZ_HEALTH_MONITOR_ENABLED=false` в `tests/server/conftest.py`): фоновый опрос не должен
   ходить в сеть за спиной сценария. Там, где мониторинг проверяется, цикл запускается явно
   (`run_cycle`, `HealthMonitor.poll_once`) с транспортом `httpx.MockTransport`.
5. **`busy`/сессии/пути не кэшируются.** Они приходят только по кнопке «Проверить сейчас»:
   хранить их значило бы показывать устаревшие данные, поэтому карточка честно помечает, что это
   ответ агента на момент запроса.
6. **`POST /stores/{id}/check` — асинхронный эндпоинт** (httpx), поэтому сессию БД он открывает
   сам из `context.db` и коммитит результат; проверка прав администратора остаётся общей
   зависимостью.

### Отклонения и решения, принятые по ходу этапа

1. **Д-6: расшифровка профиля 1С — на Э4.** §5.1.1 (п. 2 расширений) требует подставлять пароль
   из «своего шифрованного профиля», но сам профиль наполняется push-ом `POST /credentials`,
   который по плану §12 относится к Э4. В Э3 сделана **точка подстановки**
   (`client/agent/credentials.py`: `resolve_password` / `apply_profile_password`) и понятное
   предупреждение в лог; пока профиль пуст, поведение остаётся как в v2 — пароль приходит в теле
   команды. Э4 подключает Fernet + DPAPI в одну функцию, эндпоинты не меняются.
2. **Мьютекс строже формулировки §7.3.** Там сказано «второй запрос **того же класса** получает
   `409`»; реализовано «любой второй запрос» — параллельные `merge` и `update-db` на одной базе
   недопустимы (I-13), и именно этого требует чек-лист Приложения A («Параллельный запуск merge
   и update одновременно → второй получает `409`»).
3. **`format_command()` маскирует пароль.** В v2 команда печаталась в лог целиком, вместе с
   `/P<пароль>`. По I-7 в лог теперь идёт `/P***`, а на выполнение по-прежнему уходит настоящий
   argv (маскируется только представление для логов).
4. **Файловые операции — `asyncio.to_thread`, без `aiofiles`.** v2 использовал `aiofiles`; в
   монорепо такой зависимости нет (requirements Э1), а логи крошечные, поэтому поведение
   `clear_log_file` / `check_log_file` сохранено 1:1, а реализация — на stdlib. Никаких новых
   зависимостей Э3 не добавил.
5. **Проверки v2 адаптированы под очередь, но не ослаблены.** В v2 `/run-*` работал через
   FastAPI `BackgroundTasks` и выполнялся до возврата ответа, поэтому тест мог проверить задачу
   «сразу». У нас операция живёт в фоновом воркере (I-8), поэтому тесты либо проверяют мгновенные
   эффекты (`202`, `log_path`, обнулённый лог), либо дожидаются обработки очереди
   (`await runner.wait_idle()`) через ASGI-клиент — при этом явно проверяются и ушедшая в 1С
   команда, и итоговый лог.
6. **`/check-files` отдаёт даты файлов в UTC с суффиксом `Z`.** Q52 требует дату файла; чтобы API
   оставался однородным (§6: все метки — UTC + `Z`), `*_mtime` считается из `st_mtime` в UTC,
   а пояс кассы на клиенте не угадывается.
7. **Живой прогон: упавший запуск 1С виден в состоянии операции, но не в `/check-*`.** Агент
   поднят с `base_1c_path`, где платформы нет: `POST /run-merge` → `202`, операция в фоне упала
   (`[WinError 2] Не удаётся найти указанный файл`), `agent-state.json` → `status=failed` с
   текстом ошибки, служба не упала, пароль в файлах кассы не найден (I-7). При этом `/check-merge`
   честно отвечает `202 in_progress`, потому что `1cv8.exe` не успел ничего записать в лог, а
   статус по логу — правило I-4 («статус только по содержимому лог-файла»). **Для Э4:** диспетчеру
   нельзя опираться только на `/check-*` — итог задачи нужно брать из состояния операции/результата
   команды, иначе «не запустилось» будет выглядеть как «идёт».

## Отчёт по этапу Э4 «Дашборд операций»

**Статус: выполнен** (13.10.2026). Спецификация обновлена до версии **1.6** (добавки Д-6, Д-7).

### Что сделано

**Сервер — диспетчер операций (`server/core/dispatcher.py`).** Вторая фоновая задача сервера
после Health Monitor: раз в `check_poll_interval_sec` (5 с) берёт незавершённые задачи из
`commands` и «доводит» их до итога:

| Что делает | Как |
|---|---|
| Отправка | `POST /check-files`, `/download-file`, `/run-merge`, `/run-update-db`, `/send-message` через `AgentClient` (§5.1.1) |
| Опрос | `GET /check-merge|/check-update-db`: `202` → `sent`/`running`, `200` → `success`, `400` → `failed`; текст лога — в `log_excerpt` и `job_logs` |
| Очередь офлайн | магазин без ответа → задача остаётся `queued`, попытки не тратятся (FR-16); уходит, как только касса появилась в сети |
| Retry | касса в сети, но запрос не удался → попытка, backoff 5→10→20 с (≤60 с), после `command_retry_max` — `error` |
| `409` от агента | на кассе идёт другая 1С-операция (I-13) → максимальная пауза, задача не теряется и попыток не тратит |
| Таймаут | дольше `command_poll_timeout_sec` (Д-7) → `timeout` |
| ФН2 | `download_file` закрывается успехом только когда `/check-files` реально видит файл, и сразу заказывает **отдельную** задачу повторной проверки (§11.3) |
| Д-6 | «залипший `202`» при свободной кассе (`/health.busy=false`) и `interrupted_operation` → `failed` с текстом причины |
| П-1 | расхождение `credentials_version` из `/health` → расшифровка `stores.password_enc` и push `POST /credentials` (не чаще `credentials_push_interval_sec`) |

Состояние живёт в БД, поэтому перезапуск сервера не теряет задачи (FR-24): очередь и статусы
`sent`/`running` подхватываются заново. Backoff и «когда последний раз сверяли версии» —
в памяти процесса, поэтому после рестарта задача проверяется сразу (это описано в отклонениях).

**Сервер — сервисный слой задач (`server/services/command_service.py`).** Создание задачи,
чистка секретов (`sanitize_params` выбрасывает `password`/`token` рекурсивно — I-7), запись
журнала с уровнями (`Ошибка`/`Error` → `error`), обрезка `log_excerpt` до
`log_excerpt_limit_bytes` с сохранением **хвоста** лога, `attempts`/`started_at`/`finished_at`,
выборки для `/jobs` и счётчик «Задач в работе».

**Сервер — API (`server/api/operations.py`).** Все точки §5.2.2 этапа:

* `POST /api/v1/admin/stores/{id}/actions` — одиночное действие, ответ `202` + задача;
* `POST /api/v1/admin/bulk/actions` — массовое (`store_ids` → `cluster` → `all`), прогресс по
  каждому магазину (`queued` / `skipped`), отключённые магазины пропускаются;
* `GET /api/v1/admin/jobs`, `GET /api/v1/admin/jobs/{id}` — история с фильтрами
  (магазин/тип/статус/«только незавершённые»), счётчики по статусам, полный журнал;
* `GET /api/v1/admin/files/matrix` — матрица «магазин × (cf/cfe/xml)» с размерами, датами,
  счётчиком «файл есть у N из M» и признаком «ещё не проверялся»;
* предупреждение Q53 при `run_merge`, если файла на кассе нет (запуск не блокируется).

Плюс `POST /api/v1/agent/commands/{id}/result` — досылка результата агентом (FR-23): закрывает
задачу, но не переписывает уже завершённую (`duplicate: true`), и не даёт чужому магазину
закрыть задачу соседа (`404`).

**Агент — приём учётных данных 1С (закрыта отложенная Э3 добавка Д-6).** `POST /credentials`
принимает `{user_name, password, credentials_version}`, шифрует пароль Fernet-ом с ключом,
защищённым **DPAPI машины** (`CRYPTPROTECT_LOCAL_MACHINE` через `ctypes`, без новых зависимостей),
и атомарно пишет профиль в `agent-config.json` (`.tmp` + `os.replace`). Дальше `run-merge` и
`run-update-db` подставляют пароль из профиля, если сервер его не передал (§5.1.1, п. 2
расширений); `/health` сразу докладывает новую версию, поэтому повторных push-ей нет. Пароль не
попадает ни в логи, ни в `format_command()` (`/P***`), ни в `commands.params`.

**UI (SPA).** Страницы `/jobs` (плитки, фильтры, статусы, «Лог») и `/jobs/{id}` (параметры,
журнал по уровням, хвост лога 1С), `/files` (матрица, «Проверить на всех/выбранные», «Разослать
ссылку» с выбором получателей), панель операций в карточке магазина (слияние, обновление БД,
проверка файлов, сообщение пользователям) и диалог массовых операций на `/stores`
(«все магазины» / «один кластер»), плитка «Задач в работе» на главной, история задач магазина в
его карточке. Всё поверх существующего `api`-клиента и Pinia-сторов (`stores/jobs.ts`,
`stores/files.ts`, `api/actions.ts` — один выбор получателя для всех форм).

### Отклонения и решения, принятые по ходу этапа

1. **Backoff и период сверки версий живут в памяти диспетчера.** В §4.3 нет колонок под «когда
   повторять» и «когда проверяли версию», а добавлять их — миграция ради таймера. Сами задачи
   хранятся в БД, поэтому перезапуск сервера их не теряет (FR-24): после старта диспетчер просто
   проверяет незавершённые задачи сразу, без ожидания backoff-а. Для 35–40 магазинов (§2 Q7) этого
   достаточно, а при переезде на несколько воркеров сервера состояние легко вынести в БД.
2. **Ожидание офлайн-кассы не тратит попытки и не истекает.** Формально `command_retry_max` —
   «попытки отправки», но если считать попыткой каждое касание офлайн-магазина, задача «сгорала»
   бы за 15 секунд вместо того, чтобы ждать появления кассы (FR-16). Поэтому `attempts` растут
   только когда магазин **в сети**, а `timeout` применяется к уже отправленным задачам.
3. **`409` от агента — отдельный случай.** Это не сбой, а работающий мьютекс (I-13): задача
   остаётся `queued` и ждёт с максимальной паузой, а не закрывается по лимиту попыток.
4. **«Залипший `202`» определяется по `/health`.** Наблюдение №7 этапа Э3 подтвердилось и на живом
   прогоне: упавший запуск 1С не пишет лог, `/check-merge` отвечает `202 in_progress`. Поэтому
   после `BUSY_GRACE_SEC` (30 с) диспетчер спрашивает `/health`: касса не занята и операции нет →
   `failed` с текстом причины. Без этого админ видел бы «идёт» до `command_poll_timeout_sec`.
5. **ФН2 закрывается по факту появления файла, повторная проверка — отдельная задача.**
   `/download-file` асинхронный и статуса не имеет, поэтому «скачано» определяется через
   `/check-files`; заодно снимок (размер/дата, Q52) попадает в `file_checks`. Повторная проверка
   создаётся отдельной задачей `check_files` (`created_by=dispatcher`), чтобы её было видно в
   истории — так §11.3 «→ затем повторная проверка» читается буквально.
6. **Настройки диспетчера добавлены в §4.9 (Д-7), а не в конфиг сервера.**
   `command_poll_timeout_sec` и `credentials_push_interval_sec` меняются из UI без перезапуска
   (`/settings`) — это ровно тот случай, для которого §4.9 и существует.
7. **SQLite: busy-timeout 30 с.** Сервер пишет в один файл из трёх мест (API, Health Monitor,
   диспетчер). Без `timeout` в `connect_args` возможны «database is locked» на коротких транзакциях;
   секунды ожидания дешевле потерянной задачи.
8. **Агент сохраняет профиль 1С по тому же пути, по которому прочитал конфиг.** Найдено живым
   прогоном: `create_agent_app` получал путь только из `--config`, поэтому при запуске через
   `MAGAZ_AGENT_CONFIG` (и при штатном старте службы) профиль оставался лишь в памяти и терялся при
   перезапуске — прямо против П-1. Теперь подставляется `default_config_path()`, если файл существует.
9. **`send_message` в живом прогоне не проверялся.** Команда вызывает `msg.exe` и `taskkill`, то
   есть показала бы окно на машине разработчика и завершила реальные процессы 1С. Логика покрыта
   тестами (`test_send_message_reports_killed_process`, mock-агент), а в прогоне шаг пропущен осознанно.
10. **`notify` на этом этапе отвечал `422`.** Уведомления — Э5; ответ честно говорил «уведомления
    появятся на этапе Э5». С Э5 действие выполняется: создаёт уведомление и ставит задачи рассылки
    (см. отчёт по Э5 ниже).

### Как работает запрет R12

- **Что проверяется.** Перед созданием задачи `run_merge` / `run_update_db` сервер ищет три
  конфликта: (1) у магазина уже есть незавершённая задача обновления (`queued`/`sent`/`running`) —
  это и есть «один `ip`»; (2) в одном запуске два магазина с одинаковой парой
  `cluster_name` + `database_name`; (3) ту же пару прямо сейчас обновляет другой магазин.
- **Что отвечает.** `409` с человеческим текстом: кто именно и что исключить из запуска. Задачи не
  создаются **вовсе** — массовый запуск не выполняется частично.
- **Что не блокируется.** `check_files`, `download_file`, `send_message`: серверную ИБ они не
  меняют. Офлайн-магазин тоже не конфликт — задача ждёт в очереди (§11.3).
- **Почему не «предупреждение».** Ответ заказчика — жёсткий запрет (R12), поэтому флага «только
  предупреждать» нет: цена гонки на 1С-сервере выше неудобства от повторного запуска.
- **Гонка двух админов.** Проверка и `INSERT` задач обёрнуты в `dispatch_guard()` (потоковый
  `RLock`): сервер работает одним процессом uvicorn (§14.1), а админские эндпоинты синхронные,
  поэтому окно между проверкой и созданием задачи закрыто.
- **Пустая база — не конфликт.** Если `database_name` не заполнен, ИБ не определена: пара
  `cluster_name` + `database_name` не сравнивается, иначе магазины «без базы» блокировали бы друг друга.
- **«Один `ip`» = «тот же магазин».** `stores.ip_address` уникален (§4.1), поэтому повторный запуск
  обновления на том же магазине отслеживается по `store_id` (§9.2 FR-28).

## Этап Э4Б: оборудование подсети магазинов (Д-1) — выполнен

Подсеть магазина опрашивает **касса**, а не сервер: туннель доводит до агента только кассу, а
камеры, свитчи и принтеры видит именно она (§3.3, §7.6). Поэтому «Проверить сейчас» — это запрос
сервера к агенту, а не скан сети с сервера дашборда.

| Слой | Что сделано |
|---|---|
| Агент | `client/agent/devices.py`: `icmp` через `ping.exe -n 1 -w <мс>` (argv, **без shell**) и `tcp` через `asyncio.open_connection`; расписание опроса и семафор (не более 16 проверок сразу); `POST /devices/config` (список + расписание), `POST /devices/check-now` (внеочередная проверка), батч `POST /api/v1/agent/devices/status` с буфером на время недоступности сервера; копия списка в `devices.json` — опрос продолжается, даже когда сервер молчит |
| Сервер | CRUD `/api/v1/admin/stores/{id}/devices` (мягкое «Отключить из опроса» — `is_active=false`), «Проверить сейчас» по строке и по магазину, сводка `GET /admin/devices/matrix`, приём батча `POST /api/v1/agent/devices/status`, push списка в `dispatcher._sync_devices` по расхождению `devices_version`, счётчики плитки в `/admin/system/info` |
| SPA | Страница `/devices`: сводная таблица «магазин × устройство», фильтры (магазин, кластер, тип, статус, поиск), действия «Проверить», «Изменить», «Отключить/Вернуть»; раздел «Оборудование подсети» в карточке магазина; плитка «Устройства онлайн / всего» на главной ведёт на `/devices?status=offline` |

### Ключевые решения этапа

1. **Серый `unknown` — это не офлайн.** Касса не ответила (или агент офлайн) → сервер пишет
   `unknown` и в логе причины, а не «нет связи с камерой» (§4.11). В UI три цвета: зелёный
   `online`, красный `offline`, серый `unknown`.
2. **Д-9: расписание опроса — серверная настройка, а не конфиг кассы.** `check_interval_sec` и
   `ping_timeout_ms` уезжают агенту в теле того же `POST /devices/config`, что и список: админ
   меняет их в `/settings` и не ходит по кассам с `agent-config.json`. `null` в теле означает
   «оставить прежние значения», поэтому старый агент без этих полей продолжает работать.
3. **Два способа проверки, потому что часть камер не отвечает на ICMP.** У устройства есть
   `check_type`: `icmp` (ping) или `tcp:порт` (TCP-connect). Порт хранится в `check_port` и
   обязателен только для `tcp`; при возврате к `icmp` форма передаёт `clear_check_port`.
4. **Только явно заведённые адреса — sweep подсети запрещён.** Ни агент, ни сервер не перебирают
   диапазоны: опрашиваем ровно то, что админ добавил в карточке магазина.
5. **Изменение списка поднимает `devices_version`.** Версия уходит агенту в `/health`, расхождение
   закрывает диспетчер повторным push-ом — тот же приём, что и для учётных данных 1С (П-1, I-16).
6. **Плитка главной и таблица — одни и те же числа.** Плитка берёт `devices_online`/`devices_total`
   из `/admin/system/info`, страница — из `/admin/devices/matrix`; «онлайн» в обоих случаях считается
   по окну `device_online_window_sec` (180 с), а не хранится в БД.

## Этап Э5: уведомления (ФН3) — выполнен

Уведомление — это не операция 1С, а сообщение людям: его показывает `TrayAgent` в сессии
пользователя, а служба только хранит очередь. Кнопка «Отложить» (П-2) не считается ознакомлением:
окно скрывается и возвращается через `notification_snooze_min`. Состав: `notifications.py` у
агента, сервис и API у сервера, страница `/notifications` и карточка отчёта в SPA.

| Слой | Что сделано |
|---|---|
| Агент | `client/agent/notifications.py`: файловая очередь `notifications.json` (§7.4) — переживает перезапуск службы и недоступность сервера; `POST /notify` (приём push-а), локальные точки `127.0.0.1` — `GET /notifications/pending`, `POST /notifications/{id}/shown|ack|snooze`; подтверждения уходят пакетом `POST /api/v1/agent/receipts` вместе с составом сессий Windows и не теряются, если сервер молчит; дублирующий канал `msg.exe */localhost` для `important`/`critical` (**без** `taskkill` — уведомление не прерывает работу 1С) |
| Сервер | `server/services/notification_service.py` и `server/api/notifications.py`: создание и адресация («все / кластер / список магазинов»), задачи `notify` по магазинам (§11.4), приём пакета подтверждений `POST /api/v1/agent/receipts`, прогресс «ознакомлены X из Y» по сессиям, дедлайн → `expired`, отмена рассылки, отчёт `GET /admin/notifications/{id}` и CSV `?format=csv`, счётчики плитки в `/admin/system/info`; действие `notify` доступно и из карточки магазина, и массово |
| SPA | Страница `/notifications`: форма создания (уровень, адресация, `requires_ack`, дедлайн, повтор, `msg.exe`), список с прогресс-баром и статусом, «Отменить», экспорт CSV; карточка `/notifications/{id}`: магазины → сессии (пользователь, статус, время показа/ознакомления, «отложено до»); плитка «Ждут ознакомления» на главной ведёт на `/notifications?status=active` |

### Ключевые решения этапа

1. **Д-10: у «Отложить» появилась своя точка агента.** В §5.1.2 были `shown` и `ack`, а кнопки
   «Отложить» из П-2 — нет. Добавлена `POST /notifications/{id}/snooze` (`127.0.0.1`), а
   `snooze_min` приезжает на кассу в теле `POST /notify`: интервал возврата остаётся серверной
   настройкой (§4.9), его не правят в `agent-config.json` каждой кассы.
2. **«X из Y» считается по сессиям Windows, а не по магазинам.** Справочника сотрудников нет
   (П-6), поэтому строки `notification_receipts` создаются по составу сессий, который докладывает
   агент: отчёт честно показывает «продавец2 — ожидание», а не «магазин получил».
3. **Отложенное не ознакомлено.** `snoozed` остаётся в незакрытых строках: числитель «X» растёт
   только от явного «Ознакомлен», а `snooze_count` и «отложено до» видны в отчёте (§4.8, П-2).
4. **Позднее `shown` не откатывает «Ознакомлен».** Пакеты подтверждений досылаются из буфера и
   могут прийти вразнобой: сервер игнорирует попытку понизить уже закрытую строку, иначе отчёт
   врал бы в пользу админа.
5. **Доставку выполняет диспетчер, а не HTTP-запрос.** Создание уведомления только ставит задачи
   `notify` (§11.4): выключенная касса получает сообщение, когда вернётся в сеть, а отмена закрывает
   ещё не отправленные задачи со статусом `canceled`.
6. **`msg.exe` — дублирующий канал и без последствий для 1С.** Для `important`/`critical` служба
   показывает окно через `msg.exe */localhost` (argv, без shell), **не** вызывая `taskkill` —
   в отличие от `/send-message` (FR-8) уведомление не имеет права прерывать работу пользователя.

### Живые дефекты, найденные при подготовке

Первые три пойманы «собачьим» прогоном CLI на реальном репозитории, ещё пять — живым прогоном
сервера с настоящим агентом и первой сборкой релиза, то есть именно тем способом, каким это
запустят на стенде:

1. **`preflight` был добавлен в парсер, но не подключён в `server.cli.main`** — команда молча
   возвращала код `1` без единой строки отчёта. Тест на парсер это пропускал; теперь есть
   `TestServerCli.test_main_runs_preflight_and_returns_report_code` и
   `test_main_prints_text_report_by_default`, которые дергают `main` целиком.
2. **Отчёт падал с `UnicodeEncodeError` в cp1251-консоли** из-за символов `→` и `≥` — проверка,
   призванная показать проблему, сама становилась проблемой. Оформление переведено на ASCII,
   плюс добавлен `console_safe()` и тест «отчёт кодируется в cp1251».
3. **`preflight --json > file` писал cp1251**: перенаправленный `stdout` на русском Windows
   работает в ANSI-кодировке, поэтому файл для протокола оказывался невалидным UTF-8. JSON
   теперь ASCII-экранированный (`\uXXXX`) — читается любым потребителем; проверено на живом
   прогоне (`raw.isascii()` и `json.loads` из файла).
4. **TrayAgent ходил к службе через системный прокси.** `httpx` по умолчанию берёт прокси из
   окружения и настроек ОС, поэтому запрос к `127.0.0.1:8383` получал `503` от прокси:
   служба была жива, уведомление в очереди лежало, а `--pending` возвращал пустоту — на кассе
   с прокси уведомления не показались бы вовсе. `client\tray\api.py` получил `trust_env=False`
   (как давно сделано в `AgentClient`), регресс-тест `TestProxyIsIgnored` поднимает настоящую
   службу на сокете и ставит «мёртвый» прокси в окружение: без исправления он падает
   с `ConnectError`. Проверка через `httpx.MockTransport` этот дефект **не** ловит — прокси
   в таком запросе не участвует, что и подтвердилось на месте.
5. **Общие ключи CLI агента работали только до подкоманды.** `magaz-agent.exe run --config …`
   — команда из docstring, из `deploy\README_INSTALL.md` и из протокола приёмки — падала
   с «unrecognized arguments: --config …»: `argparse` держал ключи на верхнем парсере.
   Теперь у каждой подкоманды есть их копия (`argument_default=SUPPRESS`, чтобы подкоманда
   не затирала уже разобранное значение), тесты — `TestAgentCliOptions`. Расхождение
   «инструкция против кода» иначе не поймать: в текстах вызов выглядел рабочим.
6. **Скрипт сборки релиза не запускался вообще.** `deploy\build_release.bat` падал сразу:
   `... was unexpected at this time`. Причина — скобки в `echo` **внутри блока**: cmd считает
   `(` началом вложенного блока, и хвост ` ...` после него оказывается неожиданным токеном.
   Строка `echo [1/3] Сборка SPA (npm ci + npm run build) ...` стояла внутри
   `if not defined SKIP_UI (...)`, поэтому скрипт не делал ничего — и `dist\release\` на этой
   машине просто не появлялся. Строки того же класса нашлись в `install_agent.bat` (2) и
   `uninstall_agent.bat` (1): на кассе установка упала бы на разборе (в пробном запуске это
   не проявилось только потому, что скрипт выходил на более ранней проверке файлов). Исправлено:
   ветвление через ярлыки (`goto`), в текстах `echo` скобок нет; регресс-тесты `TestDeployContract`
   проверяют CRLF в `*.bat`, отсутствие скобок в `echo`/`rem` внутри блоков и отсутствие
   одиночных `LF`.
7. **В спеках PyInstaller корень репозитория считался на уровень выше.** `SPECPATH` — это
   каталог спеки, поэтому `parents[1]` давал `C:\Users\...\PycharmProjects`, и сборка падала с
   «script `...\PycharmProjects\client\agent\__main__.py` not found». Исправлено в `agent.spec`
   и `tray.spec` (`Path(SPECPATH).resolve().parent`), проверка — в `TestDeployContract`.
8. **Тесты на сборочной машине трогали живую службу.** После `pip install -r
   requirements-build.txt` в `.venv` появился `pywin32`, и `agent_main(["install", …])`
   вызывался **до** проверки `service_available()`: это настоящий `HandleCommandLine`, то есть
   регистрация службы на exe с pytest, а `debug` — запуск службы на переднем плане (прогон
   повис бы, а на машине с правами администратора осталась бы испорченная служба). Исправлено:
   ветка «нет `pywin32`» проверяется с подменённым `service_available`, контракт argv — с
   подменённым `sys.modules["win32serviceutil"]`; реальная служба в тестах не вызывается.

### Что осталось (только стенд)

Разделы 2–5 протокола, то есть всё, что зависит от живой 1С и от настоящей сессии кассира:

- **ФН1**: скачивание файла по ссылке, проверка, слияние, обновление БД, `taskkill` и снятие
  блокировок при `is_fast_update = false` — требует тестовой ИБ;
- **ФН2**: рассылка файла по ссылке и распаковка архива;
- **ФН3**, что не сводится к «доставке и подтверждению» (эти шаги уже пройдены живьём, см.
  выше): окно трея с кнопками, кнопка «Отложить» через `notification_snooze_min`, окно
  `msg.exe` на рабочем столе кассира;
- сборка exe (`deploy\build_release.bat`), установка службы `MagazAgent` и задачи TrayAgent
  на чистую Windows, старт после перезагрузки, `magaz-agent.exe --console` как диагностика.

Всё это выполняется по `docs\ACCEPTANCE.md` и фиксируется в его разделах 6–8.
